## 发现的问题

### P2：封禁后的帖子可见性不一致（真实 HTTP 已复现）

在新建的隔离 PostgreSQL 数据库中创建两个账号，账号A发布带图片的帖子，账号B引用该帖子，管理员随后封禁A。结果：

| 入口 | 实际结果 |
| --- | --- |
| 原帖详情 API | 404，不可读 |
| B的引用帖详情 API | 200，`quote.unavailable=false`，仍返回A的原文和身份 |
| 原帖图片 API | 200，仍返回图片 |

引用的判定只检查原帖 visibility 和个人屏蔽关系，没有检查原作者状态：`src/server/posts.ts:28`、`:38`。媒体的公开判定也只检查帖子 visibility，没有采用帖子详情中的作者状态条件：`src/server/media.ts:67`、`:72`。

建议统一原帖详情、引用和媒体的可见性规则，补充封禁/解封回归。封禁与单独隐藏帖子的政策应在各入口一致执行，不能让用户面对原帖不可读而引用仍完整公开的状态。

复现记录：本地 `.tmp/review/banned-visibility.json`。在既有社区集成夹具的隔离环境追加诊断，实际观察为 `directStatus=404`、`quoteUnavailable=false`、`mediaStatus=200`；该诊断通过代表成功复现现有行为，不代表此缺陷已修复。临时运行脚本已清理；没有操作开发库中的账号或内容。

### P2：旧分页响应可能混入新的筛选列表（代码审查发现，未做界面复现）

`src/components/live-stage.tsx:63` 的 `more()` 不传 AbortSignal，也不检查请求所属的 path/版本。首屏请求在 path 变化时会取消，但分页请求不会取消。

触发顺序：最新列表点击“加载更多”→请求尚未返回时切换话题、搜索或推荐→新首屏先返回→旧分页随后返回。旧分页会把旧列表内容追加到新列表，并用旧游标覆盖新游标；下一次分页可能因游标绑定不同筛选而返回400。应在筛选变化/刷新时取消分页，或校验请求版本后再写入状态，并补做慢网验收。
