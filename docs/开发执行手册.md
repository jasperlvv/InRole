版本：V0.1；制定日期：2026-11-21。

目标：以手机网页为主，完成帖子、帖子与话题热搜、人物评分与戏币、个人中心四个模块，交付能邀请真实用户试用的网站。先开发浏览器版本，暂不开发原生 App。

这是一份执行计划，不代表下述功能已经实现。当前确认本机 Node.js、npm、Git、VS Code 可用；GitHub、Supabase、Vercel 的连接仍待验证。

## 0. 固定工作方式

### 工具分工

| 工具 | 负责什么 | 何时用 |
| --- | --- | --- |
| Codex（当前对话） | 产品文档、实际代码、数据库迁移、接口、调试、检查和测试 | 每个开发步骤的主力 |
| v0（可选） | 页面视觉探索和原型 | 阶段 2；不要求购买，不作为前置条件 |
| VS Code / 浏览器 | 查看文件、终端、亲自操作验收 | 每一步 |
| Git / GitHub | 保存代码和恢复点 | 每个通过验收的任务 |
| Supabase 控制台 | 数据库、认证、后续头像存储 | 阶段 4 起；它不是 AI |
| Vercel 控制台 | 网站、服务端接口、预览与正式部署 | 阶段 1、9；它不是 AI |

技术固定为 Next.js App Router、TypeScript、Tailwind CSS、Supabase PostgreSQL/Auth、Vercel。包管理器使用 npm，提交锁文件；初始化后固定依赖版本，升级另立任务。不要同时使用多个工具修改同一份代码。

不需要为应用额外购买模型 API。第一版的内容由真人创作，AI 主要用于开发。不要同时学习两套后端或提前引入 Docker、Redis、Kubernetes。

### 每个任务的操作循环

1. 在当前项目对话发送任务编号，例如「执行 3.2，先阅读需求文档」。
2. Codex 检查现有文件，完成代码和必要检查。
3. Codex 提供本地预览地址和具体操作步骤。
4. 你在浏览器按验收项操作，把实际问题原样反馈。
5. 通过后保存 Git 提交，更新进度表，再执行下一项。

一次只做一个可以验收的任务。未通过验收不得勾选完成；AI 没实际运行的检查必须写“未运行”。

## 1. 第一版产品规则（开发默认值）

- 名称：入戏 / InRole；宣传语：换个身份，说你的话。名称暂未完成商标、域名核查。
- 每次发帖、评论独立选择公共人物；用户不创建或拥有角色。
- 同一个人物可被多人同时使用。显示“人物名称 · @平台账号”，并标记用户扮演。
- 每条发言存实际作者与本次人物。发布后不能修改作者或人物；切换人物不改变旧内容。
- 平台账号 handle 唯一，公开资料不含邮箱。人物名称与 @账号分别链接到人物页和用户页。
- 帖子和评论为纯文字，去除首尾空白后 1～500 个字符；统一长度计算方法，含中文和 emoji 的边界验证保持前后端一致。
- 评论仅一级。无私信、转发、视频、关注、付费功能。账户和人物头像先使用文字头像。
- 每篇帖子关联 0～3 个话题。首版话题由管理员维护，用户搜索选择。
- 点赞按实际账号计算，一个账号对一帖一赞，可取消，与扮演身份无关。
- 人物评分 1～5 分整数，可附 1～500 字评价；一个账号对一人物一份评分，可修改或删除。评分及评价以账号展示。
- 评分榜至少 5 人评分才入榜，按均分降序、评分人数降序、人物 ID 稳定排序；未评分显示“暂无评分”。
- 每个已验证邮箱且未被封禁的账号每天首次登录自动领取 10 戏币；失败时个人中心可重试。北京时间自然日，以服务端日期为准。
- 戏币可积累、无过期；只能投给公共人物，正整数、余额充足，不能撤回；无充值、转账、提现。投币不改变评分。
- 人物停用后不可新增发言、评分、投币；已有发言仍可展示。隐藏内容与历史保留是两种不同状态。
- 用户可删除自己的帖子与评论；人物、话题、权限、余额都不能由普通用户任意修改。
- 每日币量、正文上限、榜单门槛和限流值统一配置。改规则时先改产品文档，再改代码。

## 阶段 5：帖子、评论、话题真实接口（10～16 小时）

目标：真实内容闭环；页面正式切换到真实数据。

| 编号 | 具体动作 | 工具 / AI | 交付物 | 怎样检验 |
| --- | --- | --- | --- | --- |
| 5.1 | 写接口契约：路径、输入、返回、错误码、登录要求、分页；统一校验和错误处理 | Codex | docs/api.md、类型/校验 | 网页与接口字段一致；错误不返回堆栈和密钥 |
| 5.2 | 人物读取、帖子分页读取、发帖、详情、删除、话题关联 | Codex | Route Handlers及数据服务 | A发B可见；刷新保留；author由会话确定；停用人物和不存在话题被拒绝 |
| 5.3 | 评论、点赞/取消、我的帖子评论点赞、用户公开页 | Codex | 完整互动API | 同用户切身份不增加点赞；B不能删除A内容；分页无重复遗漏 |
| 5.4 | 投稿幂等、权限、持久化限流、正文安全渲染与失效状态处理 | Codex | 防重复和防刷实现 | 快速点两次/重试只生成一次；直接请求不能绕过；恶意HTML按文本显示 |
| 5.5 | 移除正式模式假数据，补网络错误和草稿恢复；记录必要服务端日志 | Codex | 真实模式 | 断网不显示假成功；恢复后能重试；隐藏/删除帖的直接链接不能继续公开读取 |

建议接口：GET /api/identities；GET/POST /api/posts；GET/DELETE /api/posts/:id；GET/POST /api/posts/:id/comments；DELETE /api/comments/:id；PUT/DELETE /api/posts/:id/like；GET /api/topics；GET /api/topics/:id；GET /api/me/activity。按资源补充必要查询参数。

分页先选稳定游标（created_at + id），每次20项。限流初值可设：发帖每账号每分钟3次、评论10次；须由持久化服务端/数据库策略执行，不能只靠浏览器倒计时或单个进程内存。若数据库开放写入，所有写入路径也必须受同样约束。

给 Codex：

```text
执行阶段5，从接口契约和发帖最小链路开始。
页面通过统一数据服务调用真实接口，服务端校验用户和输入，数据库约束兜底。
通过数据库原子操作或受控RPC保证人物可用、作者不伪造和限流不可绕过。
为新建帖子和评论提供按用户隔离的幂等键，重复请求返回原结果。
完成A/B账号、断网重试、越权和停用人物的实际验证。
```

通过门槛：A发帖→B浏览→B换人物评论→A看到回复→点赞取消全部通过。

```text
执行阶段6。人物是公共评价对象，评价以真实平台账号发表，不附加扮演身份。
保持一人一人物一份评分，隐藏/删除评价按产品规则同步退出评分统计。
查询采用聚合或可信统计，客户端不能直接写平均分或人数。
验证两个账号评分、修改、删除与排行榜门槛。
```

通过门槛：评分和人数计算可手算核对，个人页与公开页权限正确。

## 阶段 7：戏币钱包与投币（10～16 小时）

目标：把币做成可核对的账本，不是前端改一个数字。

| 编号 | 具体动作 | 工具 / AI | 交付物 | 怎样检验 |
| --- | --- | --- | --- | --- |
| 7.1 | 实现每日领取：用户+北京时间日期唯一，服务端计算日期 | Codex | 每日发币事务/RPC | 同日登录/刷新/并发领取都只+10；客户端改时间无效 |
| 7.2 | 实现投币：余额校验、扣款、记录流水、人物收币统计在同一事务 | Codex | 投币接口、事务和幂等键 | 余额10投3后为7；余额不足无任何半成品记录；重复请求只扣一次 |
| 7.3 | 接钱包、领取状态、流水分页、人物投币弹窗、今日/累计榜 | Codex | 完整钱包UI | 页面与数据库一致；投前确认对象和数量；只本人可看流水 |
| 7.4 | 并发、故障、日期边界、金额参数和停用人物测试 | Codex | 自动化测试及结果 | 两个同时投8的请求，最多一个成功；小数/负数/超大值拒绝；不存在或停用人物拒绝 |

数据原则：wallet余额 >= 0；金额为整数；每日grant对(user,date)唯一；投币对(user,idempotency_key)唯一。人物收币从可信流水聚合或事务内维护，两者能核对。不得让普通客户端直接更新余额、插入任意领取流水。RPC若使用提权执行，必须校验auth.uid()、固定search_path并限制执行权限。

给 Codex：

```text
执行阶段7。戏币不是现实货币，不做充值、提现和用户转账。
数据库事务保证扣余额、流水、人物收币一致；账户加锁或条件原子更新防超扣。
按Asia/Shanghai自然日发放，日期由服务端/数据库生成。
新增POST /api/coin-grants/daily、POST /api/identities/:id/tips、GET /api/me/wallet。
写有意义的并发、幂等、权限和午夜边界测试；测试只用测试账号和数据库。
提供余额=领取总额-投出总额的核对查询。
```

通过门槛：并发和重试不多发、不超扣、不丢账；每笔余额变化可追溯。不能用“按钮禁用”代替事务验证。

## 阶段 8：帖子与话题热搜（6～10 小时）

### 初始算法（配置化，内测后调整）

- 统计窗口：最近24小时/最近7天，均为滚动窗口；展示“最近更新时间”。
- 帖子H=L+3C。L为窗口内新增且当前未取消的非作者点赞账号数；C为窗口内参与评论且至少有一条可见评论的非作者独立账号数。同一评论者只计一次。
- 话题T=2A+L+3C。A为窗口内发布可见相关帖子的独立账号数；L/C为窗口内对话题相关可见帖进行有效点赞/评论的独立账号数，在整个话题内分别去重，排除对自己帖子的互动。避免直接叠加每条帖热度放大刷帖。
- 排名排除被隐藏/删除内容和无效互动；按热度降序，同分按最近有效活动时间、ID稳定排序。
- 不限制帖子必须在窗口内创建，老帖有新互动仍可上榜。取消后再赞的时间行为必须明确实现，不能用累计计数冒充窗口统计。

| 编号 | 具体动作 | 工具 / AI | 交付物 | 怎样检验 |
| --- | --- | --- | --- | --- |
| 8.1 | 实现窗口统计SQL和小型可手算样本 | Codex | 统计查询与测试数据 | 老帖新互动有效；作者自赞不计；一人评论10条只算1 |
| 8.2 | 实现榜单接口与缓存/定时更新，每10分钟更新 | Codex + 托管调度配置 | GET /api/trending及作业 | 手动触发和自动触发都有日志；作业端点有鉴权；失败保留上次有效榜 |
| 8.3 | 连接帖子榜、话题榜、话题详情及时间切换 | Codex | 热搜页面真实数据 | 可点击正确内容；切换窗口结果正确；无数据不伪造热搜 |
| 8.4 | 检查删除、隐藏、限流、过期缓存与性能 | Codex | 边界记录 | 已隐藏内容即使在旧快照中也不会通过接口公开返回 |

给 Codex：

```text
执行阶段8，严格按手册窗口和去重规则计算，不用累计点赞数代替窗口互动。
先用可手算样本验证，再接UI和调度。
检查当前托管套餐是否支持10分钟调度；不支持时比较可用Supabase Cron或付费托管，记录选择与费用再配置。
作业幂等、带鉴权，记录成功失败；可见性校验不能仅等缓存刷新。
```

通过门槛：两个榜单都能解释分数来源，有真实自动更新证据。套餐不支持则选择适配方案，不假设免费套餐一定支持。
