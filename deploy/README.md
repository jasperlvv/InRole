# InRole网站候选版部署与回滚

2026-11-25；0.2.0-rc.1。这里是可审查的单节点发布材料，**不表示已完成Linux容器、正式HTTPS或公网验收**。本机无Docker引擎，实际构建/部署在第2、3步获得资源后执行。当前代码检查和隔离数据库结果见`docs/verification/R01-release-candidate.md`。

## 结构与秘密

- `compose.yaml`：PostgreSQL17.12、候选应用镜像、Caddy2.11.9、独立迁移/备份工具服务；只有Caddy发布80/443。数据库、媒体、注销回执和TLS状态分别持久化。
- `init-db.sh`：只在空PostgreSQL数据卷首次启动时创建迁移/应用角色；普通重启不重建数据库。应用没有拥有者权限，迁移凭据不传给应用。
- `.env.example`：没有真实值。复制为本目录`.env`，权限600，分别生成至少32字节随机、URL安全的密码和三个不同持久密钥。域名不带协议或路径。禁止在对话、日志、截图中展示`docker compose config`展开的秘密。
- `secrets/backup-key`：至少32字节高熵随机材料；目录700、文件600。密钥另存受控位置，丢失无法恢复备份。Compose本地文件secret不是云端密钥管理，宿主机及Docker管理员仍能读取环境与挂载文件。
- 不提交.env、秘密、转储、备份或用户上传文件。防火墙只放必要HTTP/HTTPS与受限SSH；不要发布数据库或应用端口。

官方版本与行为依据：[PostgreSQL镜像](https://hub.docker.com/_/postgres)、[Node镜像](https://hub.docker.com/_/node)、[Caddy镜像](https://hub.docker.com/_/caddy)、[Caddy反向代理](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)。生产构建时记录实际镜像digest；本材料固定版本tag，tag本身仍可能被上游重建。

## 首次部署顺序

在Linux主机、获得批准的候选源码目录操作，确认域名/费用和适用发布要求后执行；此处没有购买或创建资源。

1. 检查目标CPU架构。构建`docker build -t inrole:候选提交号 .`，将这个不可复用的发布tag填入`.env`的`INROLE_IMAGE`；归档镜像digest和源码提交。构建期不需要真实数据库密码；`.dockerignore`排除秘密。
2. 填好本目录`.env`，创建备份密钥和`backups`目录；进入`deploy`目录，以批准配置执行`docker compose config --quiet`，检查不会输出秘密。后续命令均在`deploy`目录执行。
3. `docker compose up -d db`，等待健康；`docker compose run --rm migrate`。迁移任务部署全部追加迁移并重新应用权限，失败时不要启动正式应用。
4. 审核并导入公共目录，创建站长普通账号后使用受控工具提升管理员。原`db:seed:catalog`仅适用于本机开发，不能直接用于正式库；正式公共目录导入工具需明确目标库并审查素材。不要复制开发账号、示例帖子或余额。
5. `docker compose up -d app`，在容器内检查`/api/health`和`/api/ready`。配置DNS为真实地址；没有可用IPv6就不要发布AAAA。然后`docker compose up -d caddy`，验证证书和外网HTTPS。
6. Caddy覆盖`X-Real-IP`，应用仅相信该值。前面再套CDN/代理时必须重新配置可信代理链，不能继续把边缘代理地址当用户IP，也不能直接信任用户传来的转发头。首版不缓存账号/API或受控媒体。
7. 验证根路径真实社区、`/demo`独立、媒体上传/Range播放、实际Origin、登录Cookie、密码恢复、全部权限与钱包；外网验收另需大陆及海外的真实证据。尚未选托管区域，所以隐私政策中的托管信息与正式保存期限必须在公开前补齐。

`Dockerfile`保留迁移CLI依赖以支持同一候选镜像的工具任务。应用以node用户运行；媒体与注销回执卷首次创建时从镜像的1000:1000目录初始化。升级或迁移卷后需核对所有权，不能以开放777代替修复。

## 备份与恢复

备份工具镜像含PostgreSQL17工具和独立Node脚本：`docker compose build ops`。加密使用AES-256-GCM，带随机nonce和认证标签，密码错误、截断或篡改会失败。加密模块已在Windows验证二进制还原、篡改/错钥拒绝、失败无残留及不覆盖既有文件；**Linux整套备份/恢复尚未实际运行**。

运行`sh backup.sh`：取得维护锁，停止应用并等待45秒，再生成同一停写窗口的数据库及媒体快照，最后无论成功失败都尝试恢复应用。Caddy期间可能显示暂时不可用；安排低流量窗口并通知用户。不得与手工写库、部署、其他备份同时运行。脚本依赖Linux的flock和Docker Compose。

输出`backups/inrole-时间.enc`，含数据库、媒体、表数据摘要、媒体SHA256和注销标记。由服务端外独立保存的`erasures`卷保存更及时的注销回执；若回执写入失败，会输出`ERASURE_RECEIPT_PENDING`并由下次停写备份根据CLOSED账号补齐，运营者应告警处理。

备份与回执必须复制到**主机之外的受控存储**，用加密传输；备份加密密钥另存。目标位置、远端授权、保留期限和告警接收方式尚待第2步确认，当前不声称已有异地副本或自动恢复保障。初始建议每日数据库/媒体备份、主机外副本至少保留30天；这是待落实策略，不是已部署任务。删除过期副本前先确认最新备份和恢复验证成功。

恢复命令示例（只有核对当前注销回执已齐备后才设确认变量）：

```sh
docker compose run --rm -e ERASURE_JOURNAL_CONFIRMED=yes ops restore inrole-具体时间.enc
```

恢复脚本：验证加密 → 仅在空`restored_media`卷提取受限文件路径 → 新建`inrole_restore_随机ID`数据库 → 恢复全部表 → 比对所有表摘要和媒体哈希 → 应用受限权限 → 重放**当前**独立回执中的后续注销 → 清理相应媒体 → 将新媒体卷设为1000:1000。不会覆盖原库/媒体；失败保留独立恢复目标供排查。

注意：确认变量只是操作者的证据确认，不会证明回执一定最新。原主机故障时，应从最新的受控回执副本补回`erasures`卷；恢复较旧快照时须包含快照之后的注销。原主机可用时先停写，核对CLOSED账号与回执完整性。缺少这些资料时，暂停公开恢复内容并先处理隐私风险，不能直接切换上线。

新恢复卷非空时脚本拒绝继续写入；下一次演练使用新的空恢复卷/独立Compose项目，保留旧目标，不执行`down -v`来清空生产数据。恢复完成后使用新库、新媒体卷启动独立预览服务，执行账号、媒体和钱包检查，得到真实验证结果后才由批准的切换方案推广。较旧版本快照缺少当前迁移/函数时需先做独立兼容恢复方案，本脚本不保证可直接跨任意历史版本恢复。

## 自动任务与告警

以systemd timer每日调用`backup.sh`并记录退出码；不输出环境。告警至少包含应用健康/就绪失败、5xx、磁盘/媒体容量、备份失败、注销回执失败和账单异常；接收人暂定运营者，具体通道待配置。

定时运行`docker compose exec -T app node scripts/ops/purge-media.mjs`，重试已注销私人媒体的物理清理。只接受固定UUID媒体文件名，失败退出非0；删除记录状态在磁盘清理前已阻断读取。其他删除的帖子媒体保持不可公开访问，存储回收可在确定保留策略后加入专用清理，不能删除公共头像或仍被引用的合法素材。

## 升级与回滚

1. 记录当前镜像tag/digest、应用版本、迁移列表；先验证备份及恢复能力。
2. 以兼容的追加迁移升级，单独运行migrate；不在每个应用实例启动时竞争执行迁移，不修改已执行迁移。
3. 更新INROLE_IMAGE后`docker compose up -d app`，检查健康、日志和关键接口，再观察正式流量。
4. 应用回滚改回上一版镜像并`up -d app`；前提是已验证它兼容新schema和权限。**0.2.0-rc.1包含注销/原ID预留和策略变化，不得不经验证直接回退到不识别这些规则的旧应用。**
5. 数据损坏通过新库/新卷恢复再切换；镜像回退不会回退数据库。若已注销，所有回滚/恢复路径仍要遵守注销状态，不能重新启用旧会话或公开旧内容。

- 生产域名Origin/Cookie及上传/Range验证。
- 加密数据库/媒体备份、全新目标恢复和后续注销重放演练。
- 备份/回执异机副本、保留与告警的真实配置。
- 手机/电脑人工清单、大陆/海外跨网络记录。
- 托管地区、隐私保存期限和面向大陆公开发言的适用要求确认。
